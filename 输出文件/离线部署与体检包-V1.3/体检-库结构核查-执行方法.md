# 库结构核查 —— 执行方法（现场用；离线、只读、不需要管理员）

> 工具：`db-schema-check.js`（本包顶层）　入口：**双击 `体检-库结构核查.cmd`**　报告：`._env-report\库结构核查报告-<机器名>-<时间戳>.txt`
> 依据：技术债 `E71`（`measure_rt.unit_index`）、`E73`（`upload_log.fail_reason` / `updated_at`）、**`E201`（检查面必须等于现行迁移清单）**；规范 9.5 第 6 条「数据结构变更约束」。
> 检查面 ＝ `server\db\index.js` 的 `STRUCTURE_UPGRADES` **全量**：**列面 6 列 ＋ 索引面 2 个**。
> **缺列与缺索引不是同一严重度**（下面第 2 节的表就是按两档写的）：缺列会**写入报错**，缺索引只是**慢**（走全表扫）、**不影响正确性**。

## 0. 查什么（一句话）

看板库里**"后来加给既有表"的那几列到底在不在**：**列面 6 列 ＋ 索引面 2 个**（见下表）。

| 面 | 查什么 | 为什么 |
| --- | --- | --- |
| **列面（6 列）** | `op_log.team_code`（`DR-12`）／`measure_rt.unit_index`（`E71`）／`upload_log.fail_reason`＋`updated_at`（`E73`）／`shift_stat.run_sec_day1`＋`run_sec_day2`（`E83`） | 缺列 ⇒ **一写入就报错** |
| **索引面（2 个）** | `ix_op_log_team`／`ix_measure_rt_collect_time`（`E170`） | 缺索引 ⇒ **只是慢**（按 `collect_time` 取范围的查询走全表扫），**不影响正确性** |

**动机**：这几列若缺，服务跑起来"读数全绿"（结构版本一致、指纹一致、自检 `ok`），**直到真写入才报错**（如 `table upload_log has no column named fail_reason`）—— 属"开发机全绿、现场老库才炸"的形态，必须在现场实地确认。

## 1. 怎么跑

**方式 A（推荐）：双击 `体检-库结构核查.cmd`**
自动扫描：本包目录、上一级目录、桌面、文档、以及每个盘符的**一级子目录**（找 `data\**\*.db` 与 `backup\**\*.db`）。

**方式 B：把"看板程序目录"拖到这个 `.cmd` 上**
例如把 `D:\看板` 拖上去 —— 只扫该目录（含其 `data\`、`backup\`）。

**方式 C：命令行指定**
```
体检-库结构核查.cmd "D:\看板"
体检-库结构核查.cmd "D:\看板\data\prod\board.db"
体检-库结构核查.cmd                 :: 等价于方式 A
```
可选参数：`--no-report`（只打印不落文件）、`--report-dir <目录>`（改报告落点）、`--no-auto`（只用命令行给的路径）。

**方式 D：自证检查面没有漏项（2026-10-07 新增；不碰真实库）**
```
体检-库结构核查.cmd --self-test        :: 或 node db-schema-check.js --self-test
```
它用**纯内存库**（`:memory:`）把检查面的 **8 项逐一摘掉**各跑一遍（每项都必须**红并指名**；不摘 ⇒ 绿），
并（能定位到仓库时）把 `server\db\index.js` 的 `STRUCTURE_UPGRADES` **逐条解析**出来与检查面对账 ⇒
**"检查面悄悄落后于现行清单"（`E201` 的根因）从此有机器判据**。退出码：0 = 全部自证通过；1 = 有失败。

**不需要**装 Node、不需要管理员、不需要外网 —— 本包自带便携 Node（`._node\node.exe`），只在本次运行内使用，不改 PATH、不改系统。

## 2. 输出怎么读

每个库文件一行结论，最后有一行汇总（`期望 缺列 0`）。

| 看到 | 含义 | 要做什么 |
| --- | --- | --- |
| `[OK]` | **列齐且索引齐** | 无需动作 |
| `[缺列]` | 该库缺列（**结案口径未闭合**） | **启动一次**看板服务即自动补上（既有行零回填）⇒ 复查**列面必须为「缺列 0」** |
| `[缺索引]` | **列面齐**、只余索引面差异（**不影响正确性**） | 同一次服务启动也会补上（`CREATE INDEX IF NOT EXISTS`）；**它不构成结案闸门**，登记即可 |
| `[缺列]` 且报告里另有「索引面缺 …」 | 两面都不齐 | 同一次启动一并补上；**结案只看列面**，但索引面差异要在回传报告里保留 |
| 报告里的 ⚠「库里版本**已经是现行值**却仍缺列」 | **升级报成功、结构没落地**的本体形态（`E71`／`E73`／`E201` 同形） | 同上（启动一次即补）；**并在回传报告里保留这条记录** |
| `[SKIP]` | 打不开（正被服务独占、或不是 SQLite） | **不要当通过** —— 关掉服务再扫一次，或把该文件单独发回 |
| 汇总行「列面…缺列 0」 | 列齐（结案） | 结案；索引面那一行另看 |

**关键：缺列 ≠ 数据丢失。** 迁移只做 `ADD COLUMN`（既有行保持原样，新列为空值），不删列、不改列、不回填。

## 3. 闭环三步（"环境待确认项"的结案方式）

1. **扫基线**：在**每台跑过看板的机器**上跑一次（现场机、开发机、以及任何放着备份的机器），把报告回传。
2. **部署修复后的构建**，并在**每个库所在机器启动一次**看板服务（启动时 `initSchema()` 会无条件逐条执行迁移步骤）。
3. **复查**：再跑一次本工具 ⇒ 汇总行必须是 **`缺列 0`**。

> **恢复旧备份后也要启动一次服务**：备份是当时那一刻的快照，直接恢复等于回到缺列状态。

## 4. 安全边界（说清"不做什么"）

- **全部只读**：每个库都以 `{ readOnly: true }` 打开 —— 不建 journal、不写库、不加锁写。
- **唯一写动作**：把本次报告文本写进 `._env-report\`（可用 `--no-report` 关掉）。
- **不改系统**：不装东西、不改 PATH、不改注册表、不联网。
- 要**零风险**：先把库文件复制一份，再对副本跑（把副本目录拖到 `.cmd` 上即可）。
- 它**不能**替你证明"现场不存在某个库" —— 只有实地跑一遍，那份"`缺列 0`"才是事实。
- **退出码（本工具自己的契约）**：`0` ＝列齐且索引齐；`1` ＝有缺列（结案口径未闭合）；`2` ＝用法/环境错误；`4` ＝列齐、**仅索引面差异**（结案口径已闭合，性能面待登记）。⚠ 刻意**不用 `3`** —— 本仓 `tests\` 的退出码契约里 `3` ＝"本环境跑不了（整脚本跳过）"，借用会让"缺索引"被读成"跳过"。

## 5. 带回什么

- `._env-report\库结构核查报告-*.txt`（**原样回传**；UTF-8 带 BOM，记事本可直接看）。
- 若有 `[SKIP]`：说明是哪台机器、哪个文件、当时看板服务是否在运行。
- 若第 3 步复查已归零：把**复查那份报告**也一并回传（它就是结案证据）。
- 若索引面有差异：在回传说明里**单独写一行**（与缺列分开写 —— 两档严重度不同，混写会让开发机误判优先级）。

## 6. 常见情况

| 现象 | 原因 / 处置 |
| --- | --- |
| `[SKIP] … 打不开` | 库正被看板服务独占（Windows 文件锁），或该文件不是 SQLite。先停服务再扫；仍不行就把文件单独发回 |
| `upload_log:表不存在` | 该库比"上传队列"功能还老（表都还没建）。启动一次服务会由 `CREATE TABLE IF NOT EXISTS` 建表 —— 但**请把这条记录回传**，它说明这台机器的库很老 |
| 扫到 `backup\` 里的库并报缺列 | **正常**，那是历史快照，不是当前库；只有"恢复并使用"时才需要按第 3 步处理 |
| 报告里中文变乱码 | 用记事本/VS Code 打开（UTF-8 带 BOM）。若用 `type` 命令看，请先 `chcp 65001` |
| 一个库都没扫到 | 说明看板程序目录不在自动范围里：用**方式 B**（把目录拖到 `.cmd` 上） |

## 7. 备注（为什么本包顶层 `.cmd` 是纯英文）

`cmd.exe` 按 OEM 代码页（中文系统 936）读取 `.cmd` 内容，UTF-8 的中文会被误解码、甚至把一行拆断（2026-09-28 实测：`set SCRIPT=%~dp0<中文>.ps1` 后 `if not exist` 报 NOTFOUND）。因此本包所有 `.cmd` **一律纯 ASCII ＋ CRLF**，文件名只作显示用；`.ps1` 则保存为 **UTF-8 带 BOM**。这条是本项目技术债 `E49` 的处置，别改。

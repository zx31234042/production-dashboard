# ADR-0006：本地库结构迁移的归口（新建结构在 `schema.sql`，旧结构重建在 `db\index.js`）

| 项目 | 内容 |
| --- | --- |
| 编号 | ADR-0006 |
| 状态 | **已接受**（2026-09-22，规划主代理依实测证据裁定） |
| 日期 | 2026-09-22 |
| 触发来源 | V1.33 批次（测试标准上下限与典型值的显示与录入）**DR-03 `standard` 重建为 (产品,工序,版本) 追加式模型**；实现座位 S 在落地时**实测复现了一个静默毁数据的写法**，提出归口问题请裁定 |
| 相关 | `server\db\index.js`（`SCHEMA_VERSION '4'`、`migrateLegacyStandard()`、`initSchema()`）、`server\db\schema.sql`、需求 **DR-03 / DR-12**（V1.33）、`tests\db-check.js` |

## D1（决策）：新建库的结构正源＝`schema.sql`；**旧结构的重建迁移放在 `server\db\index.js`**

- `schema.sql` 仍**唯一**负责"**空库建成什么结构**"：`standard` 的 14 列（含 `id`）与**唯一键 `(product_code, process_code, version_no)`**、`op_log.team_code`、各索引都写在这里；`SCHEMA_VERSION` 同步升位（本轮 `'3' → '4'`）。
- **带重建语义的迁移**（旧结构 `standard` → 新结构）写在 `server\db\index.js` 的 `migrateLegacyStandard()`：**按结构判据触发**（表存在且缺 `version_no` / `process_code` 才重建），重建后判据不成立 ⇒ **天然幂等**；`initSchema()` 把「旧结构迁移 ＋ 执行 `schema.sql` ＋ 幂等补列」包进**同一个事务**（`node:sqlite` 的 `db.exec()` 不自动开事务，实测中途报错会留下半迁移态）。
- 纯补列类升级（如 `op_log.team_code`）仍可用 `ALTER TABLE … ADD COLUMN`，但**必须可重复执行**（吞掉 `duplicate column name`），且 `schema.sql` 里同时保留该列 —— 二者不得出现"只有其一"的形态。

## D2（被否方案，均为实测不通，故不采纳）

| 方案 | 实测结果 |
| --- | --- |
| ① 把重建语句**按"每次执行"**写进 `schema.sql` | **静默毁数据**：每次 `initSchema()` 都把真实版本行替换成占位行（`process_code` 变 `''`、偏差/典型值变 `NULL`）。追加式模型下等于数据被抹掉。**这是本轮真实踩到并修掉的缺陷** |
| ② `ALTER TABLE … RENAME` 加 `IF EXISTS` | SQLite **无**该语法 |
| ③ 用 `RAISE()` 做守卫 | `RAISE() may only be used within a trigger-program` |
| ④ 临时触发器守卫 | 需要内层事务，与 `initSchema` 的外层事务冲突（`cannot start a transaction within a transaction`） |

## D3（后果与约束）

1. **任何带重建语义的语句，不得以"每次执行"形式写入 `schema.sql`** —— 这是本 ADR 的硬约束，直接对应上面那个毁数据缺陷。
2. 改表结构必须**同时**更新 `schema.sql` 与 `SCHEMA_VERSION`（"改 schema 未升版本"已有指纹门禁拦截）。
3. **旧行数据的处置**（本轮裁定，**措辞已按实测更正**）：旧 `standard` 行只含相机设定值（`set_depth`/`set_gain`/`set_frame_rate`/`set_shutter`），**新模型无对应语义** ⇒ **每条旧行迁移为一版占位行**（实现：`ROW_NUMBER() OVER (PARTITION BY product_code ORDER BY effective_from ASC, id ASC)`；实测 2 个产品号 3 条旧行 → **3 版**占位行）。**硬要求**（`tests\db-check.js` 已锁）：**产品号集合不丢**、每个 (产品,工序) 的 `version_no` **从 1 起且连续**、`process_code=''`、`created_by='结构迁移'`、**六个偏差/典型值列全 NULL**（**不把相机设定值伪装成标准值**）；**行数会变**。⚠️ 此前注释与派单里写的"按 `product_code` **归并成一版**"**与实现不符**，以本节为准（`schema.sql` / `db\index.js` 的相应注释应改成"每条旧行一版"）。
4. 门禁侧：`tests\db-check.js` 必须同时拥有 ①新列集与唯一键断言 ②**旧结构库迁移只发生一次**的断言（连跑两次 `initSchema()` 不得再次重建/清空）—— 后者是该缺陷的**防回潮**断言。
5. **生效版本取值序的边界**：需求 V1.33（C-84 / DR-03）写"`effective_from ≤ t` 的**最大 `version_no`** 行"，实现按 `ORDER BY effective_from DESC, version_no DESC`。在"**生效时间＝录入成功时刻、不手工填写**"（FR-3.19 / C-84）之下两者**等价**；仅当调用方**倒填** `effective_from`（v3 的生效时间早于 v2）时分歧（需求取 v3、实现取 v2）。**裁定**：以**需求措辞**为准；**倒填属越界用法**，`addVersion` 的调用方（迁移、测试、将来的服务层）不得倒填；若将来确需允许倒填，**必须先统一口径并另开 ADR**。

## 证据

- 实现：`server\db\index.js`（`migrateLegacyStandard()` / `initSchema()` 事务化）、`server\db\schema.sql`（仅新建结构）。
- 自证（座位 S，临时脚本在 `%TEMP%`、**不入库**）：**53 项全过** —— 唯一键生效、同 (产品,工序) 追加两版后**旧行仍在且旧值未被改写**、指定时刻取生效版本、无生效版本返回 `null`、`op_log.team_code` 可写可读、`initSchema()` 连跑 3 次结构/版本/指纹一致、旧库自动升级、删除防线（上限/`dryRun`/非法抛错且不删）。
- 门禁复现（本次落地时）：`node tests\db-check.js` → **通过 49 / 失败 1**，唯一红项＝`tests\db-check.js` 的期望列仍是旧结构（`set_depth` 等），属**测试座位待同步**，实现侧未改测试凑绿；`node tests\files-check.js` → **11/0**。
- **主代理独立复核（已完成）**：①自写临时脚本（置 `tests\._verify\`，跑完即删）**12/12 全过**（唯一键拒重、追加不覆盖、指定时刻取版本、无版本返 `null`、`op_log.team_code` 可写可读、`initSchema` 幂等、**迁移只发生一次且不伪装设定值**）；②测试座位 T3 把上述断言固化进 `tests\db-check.js`（**50 → 83/0**，并自带 **13 组定点变异**证伪）；③**主代理另做三组 D22 变异**（直接在 `server\**` 上改、跑完 **SHA-256 还原**）：**迁移判据失效 ⇒ `db-check` 83/0 → 79/4**（红项直指"第二次 `migration={migrated:true,…旧结构重建完成（5 个产品号 → 9 版占位行）`"）、**去掉唯一键 ⇒ 81/2**、**缺失组合不再整条占位 ⇒ 81/2**。

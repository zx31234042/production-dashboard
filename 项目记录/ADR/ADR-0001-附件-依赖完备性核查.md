> **用途：** 回答"后端用 Node 到底需不需要第三方包"——逐项实测 Node 内置能力与后端 6 类职责的对应关系。
> **性质：** 本文件是 **ADR-0001 决策 D4「依赖策略」的证据附件**；结论与决策本身记在 ADR-0001，不在此重复。
> **采集时间：** 2026-09-19 ｜ **环境：** Node **v24.21.0** / win32 x64（开发机）
> **方法：** 临时探针脚本逐项真实调用（起 HTTP 服务、连 SSE、写临时 SQLite 库、spawn 子进程），测后脚本已删除；本文件是**可复核的结论留痕**。
> **编码：** UTF-8（无 BOM），换行 CRLF，与 `项目记录\` 其余文档一致。

## 一、结论一句话

**17 项后端能力中 14 项由 Node 内置模块直接覆盖**，仅 3 项需要内置之外的手段，而其中 **2 项已由 ADR-0001 的决策规避、1 项需求本身允许替代格式**。

> 因此 **ADR-0001 决策 D4「严格零依赖（A 档）」成立** —— 交付包可以**不含 `node_modules`**。

## 四、一个必须记住的验证限制（沙箱，不是 Node 的问题）

本次核查中有 8 个子进程调用（`ping` / `sc.exe` / `schtasks` / `netstat` / `tasklist` / `wmic` / `powershell`）**全部返回 `EPERM`**。经反证确认，这**不是 Node 能力缺失，也不是目标机的问题**：

| 调用方式 | 结果 |
| --- | --- |
| `spawnSync(..., { stdio: 'pipe' })` | ❌ `EPERM`（errno −4048） |
| `spawnSync(..., { stdio: 'inherit' })` | ✅ **退出码 0** |

**根因：** 受限沙箱禁止程序打开**命名管道**，而 `stdio: 'pipe'` 在 Windows 上走命名管道。因此：

1. **看板主机本体程序（生产环境）不受此限** —— `sc.exe`、`schtasks.exe` 等可正常调用；
2. **但 `tests\` 自检脚本在本沙箱内无法验证"子进程类自检"** —— 这类断言只能到目标机或具有管道权限的环境跑（与既有 `browser-check` / `stress-check` 的限制同源，见 `tests\README.md` 第四节）。

> 备选（零子进程）方案：自检页的网络连通性用 **`node:net` TCP 探活**（已验证），服务存活状态改用**服务自身写心跳文件、看板读该文件**自证，即可完全绕开子进程。

## 五、复查方式

本核查为一次性实测留痕，**不随每次门禁重跑**。若要复查：

1. 按第二节逐项重跑对应内置模块（起服务、连 SSE、建临时 SQLite）；
2. 环境变化时须重测 —— 尤其 **Node 版本变化**（`node:sqlite` 需 Node 22.5+，**Node 24 才免实验标志**）与**目标机为兆芯平台时**（Q-26）。

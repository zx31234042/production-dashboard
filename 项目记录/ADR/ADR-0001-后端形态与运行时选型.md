## 一、背景与问题

1. 前端 Demo 已是"可对接形态"，但**数据全在内存**：刷新即失效，DR-01～DR-19 一条未落；
2. 需求要求的不只是"存数据"，而是 **6 类后端能力**：采集接入、判定引擎、统计核算、MES 双向、推送服务、落库归档；
3. 引入后端就必然要回答：**进程怎么分、用什么运行时、依赖从哪来**——而看板主机处于**隔离局域网**（ENV-19），交付物必须自包含；
4. 现有代码资产是 **JS**（`src\services\api.js` 适配层、`tools\mock-upper`、`tools\mock-mes`、`tests\` 11 个脚本），选型若换语言等于全部重写；
5. 当前接缝很干净：**整个看板的耦合面就是一个 `state` 对象**（`src\main.js` 产生、11 个组件消费），所以改造重点是"换掉 `state` 的产生者"，组件层不必动。

**必须解决的冲突：** 规范 9.5 禁止 `package.json` 与第三方库（为内网隔离而设），而后端落库通常需要 SQLite 驱动、WebSocket 库。

## 四、各决策的理由与被否方案

### D1 + D2 部署形态：**双进程开发 → 单进程交付**

**理由**：开发期双进程天然逼出清晰的前后端契约（`GET /api/state` + 推送通道），且**换壳时接口一行不改**——变的只是"后端跑在哪个进程里"。这两条正好逐条落到需求：崩溃隔离满足 NFR-11"单一组件异常不导致整体白屏"，进程可监管满足 NFR-09/DEP-02。

**被否方案**

| 方案 | 否决理由 |
| --- | --- |
| 开发期就用单进程壳 | 调试体验差（无 DevTools/无热改），且早期把业务逻辑写进壳里会导致双进程期测不到真实逻辑，**换壳时才发现问题** |
| 始终双进程交付 | 开机自启要点两下、看门狗要管两个进程、桌面会出现黑窗口，DEP-01"一次安装完成部署"打折 |

**为换壳必须守住的 5 条约束（否则部署期返工）**

1. 前端**只**通过 `wsSource.js` 取数，禁止 `fetch` 直连数据库/文件；
2. 静态资源**两种加载方式都要保留**：`file://` 双击（走 mock，评审用）/ 后端 HTTP 托管（走真实）；
3. 后端**只监听 TCP 端口**（HTTP + 推送），**不用命名管道或共享内存 IPC**——WebView2 与 kiosk 都走 TCP，换壳才零改动；
4. 壳只做三件事：内嵌后端、开 WebView2 指向 `127.0.0.1:<port>`、全屏与退出拦截；**业务逻辑绝不下沉到壳里**；
5. `tests\` 自检在**两种形态下都要能跑**，保证换壳后不回退。

### D4 + D5 + D6 依赖与存储：**能内置就内置**

**2026-09-19 在本机 Node v24.21.0 实测证据**（脚本为临时探针，测后已删除）：

| 验证项 | 实测结果 | 对应需求 |
| --- | --- | --- |
| `node:sqlite` 是否存在、是否需实验标志 | **内置、无需任何标志**（导出 `DatabaseSync/StatementSync/Session/backup`） | — |
| WAL 是否可用 | `PRAGMA journal_mode = WAL` → `{"journal_mode":"wal"}` | 单写多读、崩溃恢复 |
| 事务写入吞吐 | 5000 行 / **13 ms** → **384,615 行/秒** | NFR-07（要求 ≥10 条/秒，余量约 3.8 万倍） |
| 去重键 | `UNIQUE(equipCode, procOrderNo, collectTime)` + `INSERT OR IGNORE` 生效 | DR-13 |
| 曲线体积 | 160 采样点 JSON = **915 字节**；2 类曲线/任务 = 1830 字节 | DR-18/19 |
| 数据量估算 | 540 任务/天 → **0.9 MB/天 → 0.34 GB/年**（**推算前提**：单任务节拍 160 s → 每班约 180 件 × 3 班；节拍属开发假设，**待现场校准**） | DR-14（保留 1 年） |
| 在线备份 API | `backup` = function | DEP-08（每日自动备份） |

**被否方案：`better-sqlite3`** —— 它是原生模块，需要 `node-gyp` + Python + VS 构建工具，且安装时要**联网下载预编译二进制**。在内网隔离场景这是**最典型也最致命的第三方依赖**（风险类别 R3），而内置 `node:sqlite` 已经覆盖 DR-01～DR-19 的全部需求，**没有任何理由引入它**。

**D4 的完备性核查（2026-09-19 追加）**：为确认"零依赖"不是口号，另起一轮把后端 17 项能力逐项实测（HTTP/SSE、`fetch`+超时、HTTPS、静态托管、SQLite WAL/去重/备份、scrypt、`statfs`、TCP 探活、日志 gzip、CSV、看门狗、定时）：

- **14 项由内置模块直接覆盖**；
- 3 项非内置：**WebSocket 服务端**（已由 D6 改 SSE 规避）、**Windows 服务注册**（用 `sc.exe`/NSSM/任务计划等**操作系统工具**，不是 npm 包）、**Excel 导出**（需求允许 CSV，且属二期）；
- 结论：**A 档成立，交付包可不含 `node_modules`**。完整对照表与沙箱验证限制见 **[附件：依赖完备性核查](ADR-0001-附件-依赖完备性核查.md)**。

**WebSocket 服务端实测结论（决定了 D6）**：

| 能力 | 实测（Node v24.21.0） | 结论 |
| --- | --- | --- |
| WebSocket **客户端** | `globalThis.WebSocket` = function | **内置，可直接连上位机/MES 的 WS（IF-D 用得上）** |
| WebSocket **服务端** | `http.WebSocketServer` = **undefined** | **IF-E 推送这一环没有内置实现** |

因此 D6 选 **SSE**：需求 IF-E.1 原文是"本地实时推送（**WebSocket/SSE**）"，**两者并列，SSE 合法**；服务端用 `node:http` 分块推送 JSON 约 30 行，浏览器端 `EventSource` 一行代码，**零依赖零协议风险**。

**被否方案**：① 引 `ws` 包——为一条本可用 SSE 满足的链路引入 npm 依赖，与准则 1 冲突；② 手写 RFC 6455 服务端——能写（握手用内置 `crypto` 算 `Sec-WebSocket-Accept`），但有掩码/分片/ping-pong/关闭握手等踩坑面，**用不必要的手写协议换取"名义上的 WebSocket"不划算**。

### D7 存储粒度：**500 ms 原始帧不落库**

**理由**：需求对高频的两处要求是**实时显示**（IF-D.8，100～500 ms）与**曲线按任务固化**（FR-3.15、DR-18/19，1 s 采样），**没有任何一条要求把 500 ms 原始帧长期保存**。落库只保留 1 s 采样，数据量降到 **0.34 GB/年**。

**被否方案**：全量落 500 ms 原始帧 —— 数据量升一个数量级，且对验收项（曲线、统计、台账）**没有增量价值**，纯粹增加磁盘与备份成本。

> ⚠️ 本决策**需要向 Q-21 澄清**：上位机若坚持 500 ms 推送，我方接收侧**照收照显示**（满足实时性），但**落库按 1 s 抽样**。这条须写进接口确认单，避免联调时以为"没存全"。

### D8 前端取数通道

**理由**：这是 D1→D2 能平滑换壳的**唯一前提**。同时保留 `file://` 双击能力 = 保留"甲方/评审随时双击看界面"的能力（也是 `PROJECT_RULES` 9.5 第 1 条技术约束的初衷），并把 UI-15"演示/调试模式"落在这里。

## 五、后果

**改善**

- 交付包**可以不含 `node_modules`** → 内网隔离风险类别 **R2（依赖获取）、R3（原生编译）、R4（运行时外联）、R5（交付后乱装）一次性消除**，只剩 R1（运行时本体），用官方预编译 zip 解压即用即可解决；
- 与 `PROJECT_RULES` 9.5 **不冲突**（A 档零依赖），规范无须为后端开后门；
- `src\services\api.js` 的报文适配、13 字段组装、退避补传逻辑**可整段上移到服务端复用**，`tools\mock-upper`/`mock-mes` 直接充当联调对端。

**必须接受的代价**

1. **推送用 SSE 而非 WebSocket**（需求允许，但要在接口文档里写明，避免以后有人按 WS 去联调）；
2. **SSE 是单向的**：看板→后端的写操作（维保录入、公告发布、异常闭环、参数配置）走**普通 HTTP POST**，不共用推送通道；
3. 壳方案使**部署期前端不再以 `file://` 为主路径**，`file://` 降级为演示/调试模式。

**风险与遗留**

| # | 风险/遗留 | 处理 |
| --- | --- | --- |
| 1 | **内存验收口径**：4K 页面浏览器进程组实测约 2 GB（含共享页重复计数），而 NFR-05 要求常驻 ≤1.2 GB / 峰值 ≤1.8 GB；**WebView2 同样是 Chromium 多进程，并不会更省** | **必须在硬件到货时按"整机口径"重测并写进验收口径**，否则现场验收会被卡。**列入风险清单** |
| 2 | `node:sqlite` 要求 **Node 24 LTS**（Node 22.5+ 有但为实验性，需标志） | 运行时基线写死 Node 24 LTS；**兆芯平台须实测**（并入 Q-26 我方自办项） |
| 3 | WebView2 依赖 Edge WebView2 Runtime（Win10 可能需预装） | 并入 Q-26 实测项；ENV-14 允许安装运行时 |
| 4 | 界面字体等资源不得引用任何外网 | 新增 `tests\offline-check.js` 断言交付包零第三方依赖、零外网 URL |
| 5 | D3 运行时未定，下列产物形式未定 | 待 D3 拍板后补 ADR-0002 |

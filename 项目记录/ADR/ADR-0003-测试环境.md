## 一、背景与问题

1. **测试基建是单边的**：前端测试环境已相当完整（假 DOM、无头 Edge + CDP、确定性基准图、8 小时长跑），**服务端为零**；
2. **测试会碰生产数据**：数据落库后，"跑个用例"就可能写脏真实库；SQLite 的 WAL 与并发访问会让"服务持锁、测试写入"出现随机失败；
3. **用例互相污染**：共用库时前一个用例残留的行会让后一个用例的统计断言出错 —— 典型的"单跑过、连跑挂"；
4. **时间相关用例不可重复**：班次边界（08:00/16:00/00:00）、跨零点归属、累计运行（日/月/年）等用例若要验，必须能**控制"现在几点"**；
5. **门禁要手敲 7 条命令**：没有统一 runner，容易漏跑；改一处只跑一条脚本会掩盖连带失败；
6. **零依赖约束**：ADR-0002 D13 明确"不引入任何 npm 依赖"，因此**不能用 Jest/Mocha/Vitest**，也不能建 `package.json`。

## 四、各决策的理由与被否方案

### D14 自写 `check()` + 统一 runner（不引测试框架）

**理由**

1. **零依赖是硬约束**：`node:test` 虽为 Node 内置（实测 Node 24 可用），但改用它会与**现有 11 个脚本风格割裂**，且 `tests\README.md` 第三节的"门禁数字权威值"机制是按现有风格统计的，混用两种风格会让口径难以维护；
2. **现有风格已被验证**：11 个脚本、236 项断言、退出码 0/1 约定已稳定运行，`docs-check` 也在校验这套口径；
3. `node:test` 的便利（用例隔离、`before/after`）由 **D17 的 `harness.js`** 以"进用例前建库、退出自动清理"的方式补上。

**被否方案**

| 方案 | 否决理由 |
| --- | --- |
| 引入 **Jest / Mocha / Vitest** | 直接违反 ADR-0002 D13（零 npm 依赖）与 NFR-25（内网隔离） |
| 改用内置 **`node:test`** | 非技术性问题而是**一致性与口径问题**：两种风格并存更难维护，且要重做门禁数字统计 |
| 继续手敲 7 条命令、不做 runner | 必然漏跑；第七章自查清单无法机械化 |

### D15 统一 runner

**理由**：目前跑全量门禁要手敲 7 条命令（浏览器类还要单独处理权限），实际执行中很容易只跑"自己改动相关的那一条"，从而漏掉连带失败（例：改了 `variables.css` 注释也可能影响 `contract-check` 的常量集中化断言）。

**实现要求**：每个脚本输出行必须包含可解析的汇总（沿用现有 `通过 N 项，失败 N 项，跳过 N 项` 格式）；runner 汇总各脚本结果并**在任一失败时非零退出**。

### D16 环境与目录隔离

**理由**：这是**唯一能防住"测试写脏生产数据"的机制**，必须在写第一行落库代码**之前**定下来 —— 事后补会面临"已经有一堆代码硬编码了路径"的返工。

| 环境 | 数据目录 | 用途 |
| --- | --- | --- |
| `dev` | `data\dev` | 开发自测 |
| **`test`** | **`tests\._verify\data\test`** | **自检脚本专用（已被 `.gitignore` 忽略）** |
| `prod` | `data\prod` | 交付运行 |

**硬规矩**：① `DSH_ENV` 默认 `dev`；② 测试进程启动时若发现 `DSH_ENV=prod` **立即报错退出**；③ 业务代码**不得**出现硬编码路径，统一走 `platform\paths.js`（ADR-0002 D11）。

### D17 夹具与临时库策略（含时钟注入与错误注入）

**理由**：这三件事直接决定用例能不能验"边界"和"失败路径"。

| 夹具 | 解决什么 | 对应需求 |
| --- | --- | --- |
| `harness.js` | 每用例一个临时库（`mkdtemp` + WAL）、跑完删；服务实例启停、端口分配 | 防污染、防 WAL 抢锁 |
| `fixture.js` | 确定性样本（设备/工单/标准/测量帧/曲线），**固定种子** | 用例可重复 |
| `clock.js` | **可注入时钟** | FR-4.16 班次边界、跨零点、累计运行 |
| 错误注入 | 让 MES 上报失败、让上位机断连 | IF-B.9 补传、IF-D.9 降级 |

> **「时钟注入」是本 ADR 里最有技术含量的一条**：不注入时钟，班次边界用例只能"看运气跑"（07:59 与 08:01 结果不同）。现有 `src\services\mockData.js` 已是"把 `now` 传进来"的写法，服务端沿用即可，不构成额外负担。

### D18 跨文档一致性检查转正

**理由**：2026-09-19 的一次性交叉验证（8 份文档、35 项断言）**抓到 3 处真缺陷**，其中 2 处（README 缺字段数、规范 9.5 与 ADR-0002 口径冲突）**单看任何一份文档都发现不了**。这类检查每次新增/大改文档都该跑，写临时探针不可持续。

## 五、后果

**改善**

- 服务端测试有与前端**同风格、同口径**的夹具层，`run-all` 一条命令跑全量；
- **测试不可能污染生产数据**（D16 在机制上保证，而非靠自觉）；
- 班次边界与失败路径**可验**（时钟注入 + 错误注入），而不是留到联调时才发现；
- 跨文档口径矛盾能被门禁挡住（D18）。

**必须接受的代价**

1. 没有测试框架的用例组织能力（无 `describe` 嵌套、无自动并发）—— 由 `harness.js` 部分补偿；
2. 每个后端自检脚本都要**自己实现**夹具的建/清（约 5～10 行样板），可接受；
3. `run-all` 串行执行，全量跑一遍比并行慢（当前量级可忽略）。

**风险与遗留**

| # | 风险/遗留 | 处理 |
| --- | --- | --- |
| 1 | 夹具层若设计不当，用例仍可能隐式共享状态 | 约定"**一个用例一个库**"，并在 `db-check` 里加一条"连跑 3 次结果一致"的断言 |
| 2 | 时钟注入要求业务代码**所有**时间来源都走 `clock`，漏一处就会导致用例不可重复 | 在 `tests\` 加断言：业务代码不得直接 `new Date()`（如为可测性必要，须经 `clock` 包装） |
| 3 | 测试产生的临时库/日志可能被误提交 | 全部落 `tests\._verify\`（已忽略）；`docs-check` 已有"甲方原件/临时文件不入库"检查，后续补充 `.db` 检查 |
| 4 | 浏览器类脚本（`browser-check`/`overlap-check`/`stress-check`）在受限沙箱跑不了 | `run-all` 须**明确跳过并提示原因**，不得静默当成通过 |

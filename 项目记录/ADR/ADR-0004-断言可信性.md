## 一、背景与问题

1. **门禁的数字可信 ≠ 断言有效**：`run-all` 报"429 通过"只说明"这些断言跑过了且为真"，不说明它们**验到了该验的东西**。R-2026-09-19-02 已实证三种失效形态：
   - **零断言被判通过**（P1-2：`browser-check` 等三个脚本一个断言没跑却记 PASS）；
   - **证据不对题**（P2-9～12：`trace-check` 里 13 条条款挂到与自身无关的断言上）；
   - **恒真/恒假断言**（P1-3：候选目录为空时只跑"自比"就报 11 项全过）。
2. **写断言时存在两类系统性出错方式**（本次修复轮的实际记录）：
   - **A 类 · 前提未验证 → 断言空洞或恒假**：例：`maxDelete=0` 那条断言假设"库里有够旧的行"，实际前序用例已把旧数据删空，`total=0` 本就不该抛；若当时把期望改成"不抛"，它就变成一条**永远通过、永远验不到东西**的断言。
   - **B 类 · 期望值靠推导而非实测**：例：把 `now=0`/空串当成非法（实际是假值、走"缺省即当前时间"兜底）；把累计运行的 `month/year` 增量期望写成"不变"（实际应与 `day` 同步 +N）。
3. **"防回潮断言"本身没有被验证过**：新加的断言声称"能挡住旧缺陷"，但**没有任何机制检查它真的能挡住**。P1-1/P1-2/P1-3/P2-6 的反证都是**手工临时做的**，做完就没了。
4. **既有夹具层的空白**：`tests\lib\assert.js` 只有 `check/skip/section/finish`，**没有"前提"概念** —— 前提失败与实现失败在输出里长得一模一样，靠人工回读才能分辨。

## 二、评估准则

| # | 准则 | 来源 |
| --- | --- | --- |
| 1 | **零第三方依赖**（不得引入变异测试框架或断言库） | ADR-0002 D13、NFR-25 |
| 2 | 不破坏既有输出契约（汇总行三字段、退出码语义） | ADR-0003 D15；规范 9.5-5 |
| 3 | 断言失败要能**区分"前提塌了"与"实现错了"** | 本次 A 类教训 |
| 4 | 期望值必须**可追溯到实测**，而非推导 | 本次 B 类教训 |
| 5 | 防回潮断言必须**可证伪**：按旧实现跑必须失败 | R-02 P1/P2 的验收口径 |
| 6 | 成本可控：不给每次改动增加分钟级负担 | 工期约束（12 月底终验收） |

## 三、决策

| 编号 | 决策 | 状态 |
| --- | --- | --- |
| **D19** | **断言即证据**：门禁数字只证明"断言跑过且为真"，**不得**据此宣称"某模块已被验证"；宣称覆盖必须给出**具体断言出处** | 已接受 |
| **D20** | **前提独立**：`tests\lib\assert.js` 新增 `t.requires(name, ok, detail)` —— 前提不成立时**不进入该段**，在汇总中**单列"前提不成立 N 项"**并使退出码非 0 | 已接受 |
| **D21** | **期望值实测**：涉及行为变更的断言，其期望值**必须来自实跑观测**（先打印真实返回值，再写进断言）；断言 `detail` 应能反映实测值 | 已接受 |
| **D22** | **防回潮断言须可证伪**：新增的防回潮断言**必须配一次定点变异验证**（按旧实现/错误实现跑必须失败），该验证在 `harness-check` 中以常设暗桩保留 | 已接受 |
| **D23** | **静态防空洞断言**：静态检查 `tests\*.js` 中可疑的恒真/恒假断言形态（如与字面量 `0`/`''` 比较、`check` 的第二实参为未定义标识符） | 已接受 |

## 四、各决策的理由与被否方案

### D19 断言即证据

**理由**：R-2026-09-19-02 的 P2-15 直接指出 —— `platform\log.js` / `id.js` / `paths.js` 与 5 个 repo 函数**不在任何门禁断言内**，而当时门禁报"381 通过"；`log.js` 的 `keepDays` 未接线就是这么漏过去的。**数字口径会被误读成覆盖口径**，这是本项目已经付过代价的误读。

**落地要求**：报告/记录里凡出现"已验证/已覆盖"，必须同时给出**脚本名 + 断言名**；门禁数字旁边不得再出现"说明 X 已被验证"这类推论式表述。

### D20 前提独立（`t.requires`）

**理由**：A 类错误的本质是**把"前提"写成了普通断言**。前提塌掉时，普通断言给出的是一条与实现错误无法区分的 FAIL，于是要么被当成实现 bug（浪费排查），要么被顺手放宽期望（变成恒真断言）。**分开表达**能同时解决两件事：报告里一眼看出"这段根本没验到"，以及防止"放宽期望"这种悄悄发生的自欺。

**语义约定**

| 项 | 行为 |
| --- | --- |
| 前提成立 | 不计数（不是断言），继续执行该段 |
| 前提不成立 | 汇总里单列"前提不成立"，**不进入该段**，退出码非 0 |
| 与 `skip` 的区别 | `skip` 是"环境不满足、本用例不适用"（不算失败）；`requires` 是"**该用例的前提假设被破坏**"（算失败，必须查） |

**被否方案**

| 方案 | 否决理由 |
| --- | --- |
| 继续用普通 `check` 表达前提 | 正是要解决的问题：无法区分"前提塌"与"实现错" |
| 前提失败时自动 `skip` | 会把"前提假设错了"悄悄降级为"环境不适用"，等于放过 |
| 让每条断言自带前置校验（隐式断言库风格） | 改动面过大，且与现有 12 个脚本的写法割裂（违反 ADR-0003 D14 的一致性理由） |

### D21 期望值实测

**理由**：B 类错误 4 次全都不是逻辑难，而是**用"我以为"代替"我测到"**。实测一次的成本是几秒钟的探针；推断错一次的代价是一条假过断言（可能长期潜伏），账算得很清楚。

**落地要求**：①写新断言前，先用探针脚本或 `node -e` 打出**真实返回值**；②把该值写进断言的 `detail`（如 `实测 daySec=3720`）；③断言失败时**先打实际值再改期望**，禁止"把期望往实际值上凑"而不解释为什么实际值是对的。

### D22 防回潮断言须可证伪

**理由**：一条"声称能挡住旧缺陷"的断言，如果按旧实现跑**也通过**，那它是无效的 —— 而这种情况从输出上完全看不出来。本次 P2-6 的反证（按旧写法构造 → `rmSync` 报 `EPERM`）是**手工**做的，P1-3 是手工对拍，都没有沉淀成常设能力。**把反证变成常设暗桩**，等于给"防回潮断言"再加一层门禁。

**范围**：**只对防回潮断言做定点变异**，不做全量变异测试（后者会让门禁变重，违反准则 6）。定点暗桩放在 `harness-check`，形如"若把 X 退回旧写法，则断言 Y 必败"。

**被否方案**

| 方案 | 否决理由 |
| --- | --- |
| 引入变异测试框架（Stryker 等） | 违反 ADR-0002 D13 零依赖 |
| 全量变异测试（自写） | 成本与收益不成比例；本次的真实缺陷集中在少数防回潮断言上 |
| 不做，靠人工反证 | 已证明会随人员/时间流失（本次两处反证仅存在于对话里） |

### D23 静态防空洞断言

**理由**：A 类错误里"恒真式"的部分（与字面量比较、比较对象是 `undefined`）可以**在写下的那一刻**就被机器拦住，成本极低。这是 D20/D21 之外的最后一道网。

**发现的处理方式**：`files-check` 或 `harness-check` 报告可疑位置；**能确证为空洞的判 FAIL，仅可疑的以警告列出**（避免制造假失败，参见 ADR-0003 D18 对措辞敏感断言的教训）。

## 五、后果

**改善**

- "门禁通过"与"模块已验证"在表述上被强制分开（D19），避免把数字口径当覆盖口径；
- 前提塌掉立刻可见，**不会再悄悄变成恒真断言**（D20）；
- 期望值有实测出处，断言的可信度可追溯（D21）；
- 防回潮断言自身被验证，"声称能挡住"变成"确实能挡住"（D22）；
- 空洞断言在写下的当刻被拦（D23）。

**必须接受的代价**

1. 断言代码变长：每条带前提的用例多 1～2 行 `requires`；
2. `t.requires` 与 `t.skip` 语义相近、**易误用**（需在规范与 `assert.js` 注释里写清判据）；
3. 定点变异暗桩需要**随实现演进同步维护**（旧实现写法变了，暗桩要跟着改），否则暗桩本身会失效；
4. 期望值实测让"写断言"多一个探针步骤，速度略降。

**风险与遗留**

| # | 风险/遗留 | 处理 |
| --- | --- | --- |
| 1 | `requires` 被滥用成"什么都是前提"，导致真正该失败的实现问题被降级 | 约定判据：**前提只描述"数据/环境必须处于某状态"，不得描述"被测函数的返回值"** |
| 2 | 定点变异暗桩本身也可能失效（暗桩写法与旧实现不再对应） | 暗桩必须**内联旧实现片段**并断言"该片段在本用例下必然违反断言"，而非依赖外部文件 |
| 3 | D23 的静态检查可能误报（如合理的 `x === 0` 边界断言） | 只对"注定恒真"的形态报 FAIL，其余降级为警告 |
| 4 | 既有 429 项断言**不会**因此自动变可信 | 本轮只对 P1/P2 新加的防回潮断言做定点变异；存量断言的证据不对题问题由 R-02 的 P2-9～12 单独处置 |

## 附录一、D21 的落地口径下调（2026-09-19 追加，不改上文原文）

**结论：D21 只作为「编写约定 + 评审纪律」，不做机制化。** 理由是复查后明确了 B 类错误与 A 类**危险程度差一个量级**：

| | A 类（前提未验证） | B 类（期望值靠推导） |
| --- | --- | --- |
| 发现时机 | 可能**永远不发现**（断言恒真/恒假，一直绿着） | **下次运行立刻红**，实际值就在输出里 |
| 危害 | 静默失效，门禁数字继续骗人 | 一次红灯 + 几分钟排查，可逆 |
| 对应决策 | D20 / D22 / D23（已机制化） | D21 |

**为什么"机制化"在这里是错的方向**：从红灯到修好只有两条路 —— ①判定是期望写错 → 改期望（正确）；②不判定、直接把实际值抄进期望（危险）。**"改期望"与"抄实际值"在文本层面完全一致**，任何静态检查都无法区分；能机械化的只有"把实测值写进 `detail`"，而那是**事后文档化，不是预防**。故不再投入。

**替代方案（按性价比排序，已采纳第一条与第三条）**：

| # | 手段 | 状态 |
| --- | --- | --- |
| 1 | **构成性断言**：期望值由"已知正确的量"算出，不写手算魔数（如 `next.monthSec === prev.monthSec + addSec`，而非 `=== 7320`）—— 从根上**不需要猜数字** | **已采纳**（2026-09-19 改写 `logic-check` 的 P2-4、`db-check` 的 P2-2 相关断言） |
| 2 | 强制 `detail` 含"实测="格式 | 不采纳：只提升可复核性、不防发生，且会误伤大量合理断言（与 D23 首版误报同一类问题） |
| 3 | **评审纪律**：断言变红时，记录"改的是实现还是期望，以及为何实际值是对的" | **已采纳**（写进规范 9.5-5） |
| 4 | 静态检查"只改期望不改实现" | 不采纳：需 diff 分析，零依赖下很别扭，且易误判 |

**残余风险（如实记录）**：若实现本身错了、而有人把期望凑上去让它变绿，该错误行为会被"固化为断言"，直到联调或现场才暴露。此风险取决于**评审严格程度**，不取决于断言机制；本 ADR 不假装它能被门禁解决。

**顺带记录一次自伤**：在写"引用常量而非写死数字"的断言时，我一度写出 `RETENTION_MAX_DELETE === 5_000_000` 这种**循环断言**（拿测试里刚写的期望去比对模块里的同一个值，等于什么都没验），当场识别并删除。

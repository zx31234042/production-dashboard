## 一、背景

ADR-0001 已定下 8 项决策，唯 **D3 运行时选型**待定。为决策，另做了两轮实测：

1. **Node 侧依赖完备性核查**（→ `ADR-0001-附件-依赖完备性核查.md`）：后端 17 项能力中 **14 项由 Node 内置模块直接覆盖**，3 项非内置且已被决策规避或需求允许替代；
2. **C# 侧依赖审查与对比**：实测开发机环境、`winsqlite3.dll` 能力、交付体积构成。

## 三、两侧审查要点（实测证据）

### Node 24 LTS

| 项 | 结果 |
| --- | --- |
| 17 项后端能力 | **14 项内置直接覆盖**（HTTP/SSE、`fetch`+超时、HTTPS、静态托管、SQLite WAL/去重/备份、scrypt、`statfs`、TCP 探活、日志 gzip、CSV、看门狗、定时） |
| 库表能力 | `node:sqlite` **内置、无需实验标志**：WAL、事务 5000 行/13 ms、`UNIQUE` 去重键、在线 `backup` |
| 依赖数量 | **0 个 npm 包** → 交付包**不含 `node_modules`** |
| 交付体积 | 官方 zip ≈ 60～120 MB（`node.exe` 本体实测 89.2 MB），解压即用 |
| 服务化 | ⚠️ **Node 无内置 Windows 服务注册** → 需外部手段（见第五节） |
| 现有资产复用 | **100%**：`src\services\api.js` 适配层、`tools\mock-upper`、`tools\mock-mes`、`tests\` 11 个脚本全为 JS |
| 开发机现状 | **已具备**（v24.21.0），**可立即开工** |

### C# / .NET

| 项 | 结果 |
| --- | --- |
| 落库路线 | P/Invoke 直连系统 `winsqlite3.dll` 实测 **SQLite 3.51.1**、WAL、200 行事务 6 ms、**JSON1**、**FTS5** 全部可用 —— **能力齐备**，但该 DLL 属 Windows「设备扩展 API」清单、**非面向桌面应用的受支持 API**、版本随系统变 → **不宜作基石**；稳妥走 NuGet `Microsoft.Data.Sqlite` + `SQLitePCLRaw.bundle_e_sqlite3` |
| 服务化 | ✅ 原生 `ServiceBase` / `UseWindowsService()`（**在 Linux 上优势消失，由 systemd 承担**） |
| 交付体积 | ✅ self-contained ≈ 65～75 MB；**Native AOT ≈ 10～20 MB**（最小） |
| 生态支持 | ✅ 微软主线官方包齐备 |
| **开发机现状** | ❌ **无任何 .NET SDK、无 VS**，仅有**已 EOL 的 .NET 6 运行时** → **当前编译不了**，须先装 SDK |
| 版本约束 | .NET 8 / 9 均于 **2026-11 结束支持**，而项目 12 月底终验收 → 须上 **.NET 10 LTS**（支持至 2028-11） |
| 资产复用 | ❌ 适配层 + 两个模拟工具 + 11 个自检脚本**全部重写**，工具链变双语言 |

## 四、决策

**采用 Node.js 24 LTS 作为看板服务端运行时。**

| 编号 | 决策 | 状态 |
| --- | --- | --- |
| **D9** | 运行时＝**Node.js 24 LTS**；**交付包不含 `node_modules`**（沿用 ADR-0001 D4 的"严格零依赖"） | 已接受 |
| **D10** | **版本锁死下限**：`node:sqlite` 要求 **Node ≥ 24** 才免实验标志；运行时基线写成 **Node 24 LTS**，**禁止降到 22.x** | 已接受 |
| **D11** | **新增架构约束：平台适配层** —— 平台相关行为（文件路径、进程/服务管理、桌面壳、浏览器调用、休眠/屏保抑制）**必须收敛到 `platform/` 薄适配层**，业务代码**禁止**出现 `C:\`、盘符、`msedge`、`reg`、`sc create` 等平台字样；业务层只用跨平台能力（HTTP/SSE、SQLite、标准库） | 已接受 |
| **D12** | **Windows 服务注册用外部包装器**（`sc.exe` / NSSM / 任务计划程序）—— 它们是**操作系统工具，不是 npm 包**，不违反"零依赖"；**不为此引入 npm 包** | 已接受 |
| **D13** | **不引入任何 npm 依赖**；若将来确有必要，须**先写新 ADR** 并附离线分发方案（`nupkg`/`npm pack` 随包或私有源），同时修订 `PROJECT_RULES` 9.5 的依赖白名单 | 已接受 |

## 五、理由

1. **工期是最高权重，而 Node 现在就具备开工条件**：开发机已装 Node 24，C# 则要先装 .NET 10 SDK（且现有 .NET 6 已 EOL 必须更换）。
2. **资产复用率是数量级差异**：适配层（报文解析、13 字段组装、退避补传）、两个联调模拟工具、11 个自检脚本**全是 JS**。选 C# 等于把这些重写一遍，并把工具链变成双语言长期维护。
3. **C# 的两条优势在本项目被削弱**：
   - "原生 Windows 服务注册"—— 若后期上麒麟，服务化改由 **systemd** 承担，该优势消失；而 Node 在 Linux 下反而更省事；
   - "体积小（Native AOT 10~20 MB）"—— 60~90 MB 的差异对**另项采购的 SSD ≥512 GB**（ENV-12）**不构成约束**。
4. **零依赖目标在 Node 侧已被实测证实可落地**，交付包自包含、内网隔离风险（依赖获取/原生编译/运行时外联/交付后乱装）一次性消除，且**不改 `PROJECT_RULES` 9.5**。
5. **后期可移植性（麒麟，可能性）不影响本决策**：负责人已确认 **CPU 不变（兆芯 x86_64）**，Node 与 .NET 在该架构上均可运行，故可移植性**不是**区分因素；真正需要防的是**平台行为耦合**，已由 **D11 平台适配层**约束解决。

**被否方案**

| 方案 | 否决理由 |
| --- | --- |
| **C# / .NET 10 LTS** | 能力上完全站得住（服务化与体积更优），但**须重写适配层与全部工具链**，且在 12 月底 M6 的硬节点下，这笔成本换来的收益（省约 70 MB 体积、Windows 上服务注册更干净）**不足以抵偿工期风险**；其服务化优势在跨平台场景还会消失 |
| **Go 单文件 exe** | 交付形态最漂亮，但**资产复用率为零**、团队上手成本最高，工期风险最大 |
| **.NET Framework 4.8（系统自带）** | 交付包最小且零安装，但技术栈老旧（无 `System.Text.Json`、无 SQLite 驱动）、长期维护性差 |
| 维持"待定"继续比较 | 项目已无比较空间：两侧证据齐备，且**运行时不定就无法建表落库**（DR-01～DR-19 全部阻塞） |

## 六、后果

**改善**

- 后端可**立即开工**（建表脚本、仓储层、曲线固化均不依赖三方答复）；
- 交付包**零 npm 依赖**，内网隔离风险最小化；
- 适配层与联调工具**原样上移复用**，`tools\mock-*` 直接成为联调对端；
- 与 `PROJECT_RULES` 9.5 四条技术约束**无冲突**。

**必须接受的代价**

1. **Windows 服务注册需外部包装器**（D12）—— 属部署脚本职责（DEP-01～DEP-06 本就要写），不算额外负担；
2. **运行时版本被锁死在 Node ≥ 24**（D10）—— 升级运行时须重跑依赖完备性核查；
3. **推送走 SSE 而非 WebSocket**（承 ADR-0001 D6）—— 需求 IF-E.1 允许，但须在接口文档中写明，避免联调方按 WS 对接。

**风险与遗留**

| # | 风险/遗留 | 处理 |
| --- | --- | --- |
| 1 | **内存验收口径**（承 ADR-0001 风险 1） | 硬件到货按整机口径重测，并**提前与甲方确认验收口径** |
| 2 | **Node 24 基线与兆芯实测**（承 ADR-0001 风险 2） | 并入 Q-26 我方自办项；同时实测 4K@30Hz 与 WebView2 Runtime 是否需预装 |
| 3 | **麒麟/信创移植可能性** | 已由 D11 平台适配层约束覆盖；`后续路线图.md` 技术债 **E8** 跟踪 |
| 4 | **零依赖可能被后续需求打破**（如 FR-10.3 需要真正的 xlsx 导出） | 届时按 D13 走"新 ADR + 离线分发方案"，不静默引入 |

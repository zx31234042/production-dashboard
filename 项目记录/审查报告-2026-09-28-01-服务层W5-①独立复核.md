# W5-① 服务层（SSE 业务推送 ＋ CORS ＋ 静态托管）独立审查报告

审查座位：`review-w5a`（只读 ＋ 自写探针）。工作目录 `D:\work\vibecoding\production-dashboard`，Node v24.21.0。
本报告所有"实测"均来自我在 `tests\._verify\review-w5a\` 下自建、**现已整体删除**的探针（真起 `server\index.js`、裸 `node:net` 发请求、`node:sqlite` 查库）。仓库内既有文件**零改动**。

## 一、结论

**有条件可信**。十项自报结论中的 1、2、3（其余五类）、4、5、7、8、9、10 我独立复现成立，数值级证据见下；但**第 3 项的 `warning` 一类在正式运行路径上没有任何调用方**（只有 `judge.evaluate(input,{bus})` 这个"备好的挂钩"，全仓无生产调用点），且我另外发现 **`?since=` 大于服务端当前序号会把该客户端永久打入静默黑洞**、**优雅关闭在"有 keep-alive 在途请求"时要等约 6.35 s（接近 8 s 上限）** 两个未自报的缺陷。因此不是"不可信"（核心判据都真、都能复现），但也不能按"全绿"接收 —— 至少 `warning` 的口径表述必须更正，且上述两条应登记处置。

### C. 反向找漏洞

**C9. `eventBus` 反向找漏洞 —— 结论：隔离与边界基本扎实，`since` 矩阵有一个真实黑洞**

- 隔离：3 个订阅者中 2 个抛错 ⇒ `publish` 不抛、`handlerErrors=2`、`errors` 记录 `boom-A`/`boom-C`、正常订阅者照收；15 个连抛同样逐个隔离（`handlerErrors=15`，`errors` 有界保留）。**异步**抛错（handler 内 `setTimeout(()=>{throw})`）当然逃出同步 try/catch → 落到 `uncaughtException`（这是 JS 语义，不算本单缺陷，但值得在文件头 ⑤ 注一句"仅同步抛错被隔离"）。
- `since` 边界矩阵（容量 3、已发 5 条）：
  `-1/0/1 → hello`（`missed` 分别如实为 2/1/0 的补不齐条数）、`2/3/4/5 → replay`（`[3,4,5]/[4,5]/[5]/[]`）、`6/999 → replay 空`、`1.5/NaN/true/[]/{}/null/undefined → hello`、`'3'/'03'/' 3 '/'3 ' → replay`（纯数字串按数字解析，`' 3 '` 被 `trim()` 后合法 —— 与 `normalizeSince` 注释一致）。
- **`since > seq` 黑洞（中）**：`eventBus.js:220` 的判据 `since + 1 >= oldest` 对"游标跑在服务端前面"也成立（容量 32、`oldest=1` 时 `since=999` 照样进 replay 分支），于是回放清单为空、不发 `hello`、订阅基线被设成 999 ⇒ **之后所有事件 `evt.seq <= sub.since` 全被过滤**。实测：
  ```
  C.blackHole: requestSince=8, actualSeq=3, framesReceived=[], hasHello=false,
               pingsSeen=5, receivedAfterNewEvent=[], verdict="NO RECOVERY / NO SIGNAL"
  ```
  这是客户端**永久静默**：无 hello、无 id、无错误，只有心跳。浏览器 EventSource 断线重连时会带着那个从未被更新的 `Last-Event-ID` 重来，因此**重连也救不回来**（要刷新页面）。
- 容量 0 直接抛 `TypeError`（不静默兜底）；容量 1 正常丢最旧；`close()` 后 `subscribe` 仍返回 hello、`publish` 返回 `null` 且 `afterClose` 单独计数（不污染 `dropped`）。
- 并发（空档）验证：先 `subscribe({since:1})` 拿到回放 `[2,3]`，**同一 tick** 再 `publish` ⇒ 回放 ∪ 回调 = `[2,3,4]`，有序、不重、连续 —— 即 `subscribe` 的"同步注册 + 同步取回放清单"确实无空隙。真实事件循环里的顺序我在 B5 也验了（`?since=` 回放后新帧 seq 继续单调）。
- 严重级：**中**（见三.1）；其余为通过项。

**C10. `cors.js` 反向找漏洞 —— 结论：未找到"非回环也能拿到 ACAO"的路径**

- 判定时机：`cors.js:83` 每次请求都调 `readBind()` 取**当前** `listenAddress()`（`index.js:588-594`），不是启动时快照 —— 我以 `--host 0.0.0.0` 起服务实测所有源都拿不到 ACAO（含 `null`），说明绑定地址这条路没有绕过口。配置/env/命令行覆盖 `--host` 后仍走同一判据（`isLoopbackHost` 只有一份实现）。
- `Origin` 畸形：大写 `NULL`、`HTTP://…`、尾随斜杠、同主机异端口、`http://127.0.0.1`（无端口）、`file://`、多个 Origin 逗号拼串 —— **全部不回 ACAO**（`origins()` 是精确集合匹配，非前缀/正则）。`Origin` 缺失 ⇒ 不挂任何头、行为与现状一致。
- 敏感请求头：预检带 `Access-Control-Request-Headers: Authorization, X-Custom-Sensitive, Cookie` 时，应答固定 `Content-Type, Authorization`（不回显请求方要求）⇒ 浏览器会拦下 `X-Custom-Sensitive`，口径正确；`Access-Control-Allow-Credentials` 在所有分支都不出现。
- **低**：未注册路径不会应答预检（继续 404/405），但**仍会被挂上 CORS 头**（见 B6 补充，`cors.js:111` 与 `:114-115` 的先后顺序）。
- 严重级：**低**。

**C12. `stop()` 的 `closeIdleConnections()` 会误伤在途请求吗 —— 结论：不误伤，但也没达到它想达到的效果**

- **不误伤**（实测）：客户端只发一半 body、服务端仍悬在 `readJson` 的 `for await` 上时调 `stop()`，随后补完剩余 body —— 请求**完整成功**：
  ```
  slowStatusLine="HTTP/1.1 200 OK"  slowComplete200=true
  body: {"mount":"ifD","ok":true,"outcome":"stored","stored":true,...}
  ```
  可见 `server.closeIdleConnections()` 只回收空闲连接，不打断在途请求（与 `index.js:758-762` 的注释一致）。
- **但效果有限**（交付方未自报，**中**）：同一次停机里，那个 keep-alive 请求在停机窗口内**应答完成后**变为空闲连接，而 `closeIdleConnections()` **已经调用过了**（`:762` 在 `server.close()` 之后立即执行），不会再回收它；于是 `server.close()` 一直等对端 FIN：

## 三、发现的缺陷

### 1.（中）`?since=` 大于服务端当前序号 ⇒ 客户端静默黑洞，且重连无法自愈

- 位置：`server\services\eventBus.js:213-233`（判据 `if (since + 1 >= oldest) mode = 'replay'`，与 `oldest = ring[ringStart].seq` 比较时**只检查下界、不检查上界**），经 `server\http\router.js:120-134`（`readSince`）与 `:331-372` 暴露到 `GET /events`。
- 复现（探针，容量 32、已发 3 条事件）：
  ```
  GET /events?since=8   →  HTTP/1.1 200, 无 hello, 无任何 event:, 只有 ": ping"
  随后再 POST /ifd/frame（服务端 seq 4、5）→ 该连接仍收不到任何 event:
  C.blackHole: requestSince=8, actualSeq=3, framesReceived=[], hasHello=false,
               pingsSeen=5, receivedAfterNewEvent=[], verdict="NO RECOVERY / NO SIGNAL"
  ```
- 实测输出见上；同一场景下 `?since=0`、`?since=oldest-1` 都正常回放（`eventIds=[1..5]`），说明问题只在"游标超出当前序号"。
- 影响面：浏览器 `EventSource` 的 `Last-Event-ID` 一旦被写坏/被旧快照带偏，客户端会**永久停在无数据状态**：服务端不报错、日志无告警（`/events` 不打 warn）、前端无任何可判别信号，只能靠人工刷新页面。裸 500 ms 的 1 s 心跳会让它看起来"连接正常"。
- 建议处置（**不代改**）：把 `since > seq`（或 `since >= seq && ringLen === 0`）显式归入"游标超出服务端"⇒ 走 `hello` 快照分支（并让 `missed` 或新增字段如实说明"客户端游标领先"）；或至少回一帧可判别的 `event: hello`。D22 角度建议补一条可证伪断言：`since = seq + k` 时必须收到 `hello`，且其后新事件必须可达。

### 2.（中）优雅关闭在"有 keep-alive 在途请求"时要等约 6.35 s，接近 8 s 上限（`closeIdleConnections()` 早调了一次、之后不再回收）

- 位置：`server\index.js:754-766`（`closeAllStreams()` 后立即 `server.closeIdleConnections()`；等待循环结束后只再调一次，且那是 `server.close()` 已回调之后），配合 `server\http\router.js:392-404`（只对 SSE 主动 `sock.end()`）。
- 复现（探针）：客户端以 keep-alive 发 `POST /ifd/frame`，只发一半 body；`stop()` 在请求处理中被调用；随后在停机窗口内补完 body：
  ```
  C12a.inflightKeepAliveVsStop: bodyCompletedAt=313ms, stopMs=6353ms,
    stopRes={"code":0,"reason":"probe8-inflight"},
    responseStatusLine="HTTP/1.1 200 OK", responseComplete=true,
    clientSawCloseAfterStop=null, timedOut=false
  C12b.sseOnlyVsStop: stopMs=12ms   ← 对照：只有 SSE、无在途请求
  ```
- 关键点：**在途请求本身没被打断**（200 + `"outcome":"stored"`，数据确实落库），缺陷是"停机被对端 keep-alive 拖住"：请求在停机窗口内应答完变为**空闲**连接，而 `closeIdleConnections()` 已在 `:762` 执行过，没人再回收它，`server.close()` 只能等对端 FIN。现场上位机/MES 若保持长连接，`stop()` 会稳定吃掉 6–8 s，逼近 `SHUTDOWN_TIMEOUT_MS` 后由超时兜底（不会挂死，但"优雅退出 ≤ 数十毫秒"这一自报口径不成立）。
- 建议处置：在 `server.close()` 之后以短间隔重复 `closeIdleConnections()`（或用 `server.on('connection')` 记录 + 在每次响应 `finish` 后判定空闲再回收）；并把"有 keep-alive 在途请求也 ≤1 s"写成断言（现有夹具只覆盖 SSE，覆盖不到这条）。

### 3.（中）`warning` 事件在正式运行路径上没有任何调用方（"六类事件都挂在真实写入点"的表述不成立）

  ```
  server\services\ingest.js:706        monitorBus.publish(EVENT_KIND.LINK, payload)
  server\services\dispatch.js:765      bus.publish(EVENT_KIND.TASK, {...})
  server\repo\standard.js:268          options.bus.publish(eventKindOf().STANDARD, {...})
  server\services\uploadQueue.js:164   bus.publish(EVENT_KIND.UPLOAD, payload)
  ```

  运行时验证：连续打 `POST /ifd/frame`、`POST /ifa/dispatch`、`GET /ifd/status` 后 `busSeqDelta=2`（frame 与 task 各一），**没有** `warning`。

### 4.（低）`site.js` 的文件头声称"realpath 双保险"，实现里没有 `realpath`

- 影响面：防护强度与文档不一致；将来有人为方便在前端目录做链接（或 Windows 上建 junction）时会静默变成越权读取入口，且 D22 意义上没有可证伪断言覆盖它。
- 建议处置：要么加 `fs.realpathSync` 复核（使实现与文档一致），要么把文件头注释改成"不跟随符号链接目录（`isFile()` 拒绝目录），文件级符号链接不在防护面内"并登记风险。

### 5.（低）4 个新文件是 LF 行尾，与仓库既有 73/76 的 CRLF 现状不一致

- 建议处置：与负责人确认约定；若约定 CRLF，把这 4 个文件统一为 CRLF（属格式化，须单独一笔以免污染本单 diff）。

### 6.（低）CORS 头会挂在 404/405 响应上（白名单源）

- 位置：`server\http\cors.js:110-116`（`apply()` 在 `knownPath` 判定之前执行）。

- 建议处置：`handle()` 里先判 `knownPath`（未注册直接返回 false），再做 `apply()`；或明确登记"预检之外的响应也带 CORS 头"这一有意行为。

### 7.（低）静态托管的尾随斜杠与大小写判定自相矛盾

- 位置：`server\http\site.js:79-95`（空段跳过 ⇒ 尾随/重复斜杠被抹平）、`:93-94`（扩展名 `toLowerCase()` 后查 MIME 表）、`:87-89`（`index.html` 按字面比较）。

- 建议处置：明确"尾随斜杠是否等价"并让两条判定一致（例如扩展名判定同样按字面小写表、或统一 301 到规范 URL）。

### 8.（低）心跳断言的容差方向偏软（交付方"实测 18"能过）
